# Harmony Palette開発

現在のリポジトリ状態を基準に作業し、ユーザーの変更を保護する。

## 安全に開始する

1. `git status --short`、`package.json`、作業対象ファイルを確認する。
2. `.env.local`、Supabase Secret Key、管理者許可リスト、Cron・インポート秘密値を表示またはコミットしてはならない。
3. 承認済みスケジュール、営業情報、記事、メディアメタデータの正本はSupabaseとする。
4. ユーザーが明示的に依頼しない限り、公開、インポート結果の永続化、リモートMigration適用、メディアアップロード、本番データ変更を実行してはならない。
5. 無関係な変更と、既に作成されている検証証跡を保持する。

## 必要な知識だけ読む

- コードの所有場所、データフロー、コマンドを判断するときは[アーキテクチャ](references/architecture.md)を読む。
- インポート、DB、UI、記事、SEO、Instagram、リリース方法を変更するときは[変更ワークフロー](references/workflows.md)の該当節を読む。
- 仕様、技術、設計判断を確認するときは、ワークスペースの`knowledge/Home.md`から関連する`approved`ノートだけを読む。
- DB設定、認証、公開、Storage、Cronを変更するときは`SUPABASE_SETUP.md`を読む。
- 確立済みの画面目標があるUIを変更するときは、`design-qa.md`の該当節と関連する`audit/`画像を確認する。
- Vault全体や無関係な参考資料を毎回読み込んではならない。

## 一貫して実装する

1. 新しい抽象化を追加する前に、既存のRepository、Store、Component、Token、Routeパターンを再利用する。
2. サーバー専用Supabase Client、秘密値、権限付き操作をClient Componentへ置いてはならない。
3. 外部データは取り込み境界で正規化し、取得元URLと追跡性を保持する。不確かな解析結果を承認済みデータへ自動変換してはならない。
4. DB変更では新しいタイムスタンプ付きMigrationを追加する。適用済みの可能性があるMigrationを書き換えてはならない。
5. 公開画面の日本語は簡潔で自然にし、既存の命名、日時形式、レスポンシブ挙動、アクセシビリティラベルを維持する。
6. 記事、メディア、予定では復旧可能な操作を優先し、下書き、レビュー、公開、ゴミ箱、改訂の状態を維持する。

## 変更に応じて検証する

1. 最も対象に近いテストから実行する。
2. 文書だけの変更を除き、原則としてlintとproduction buildを実行する。
3. 視覚変更ではPC・スマートフォン、操作状態、overflow、browser consoleを確認する。
4. 選択した画面目標と比較し、実装結果の証跡だけを`audit/`へ記録する。デザインQAを含む作業でのみ`design-qa.md`を更新する。
5. インポート変更では、許可された永続化より前に非永続プレビューを実行する。
6. 挙動、データ境界、技術、重要な判断が変わった場合だけ、関連する`knowledge/`ノートを更新する。
7. 完了時に、変更内容、実施した検証、未確認の本番・外部状態を報告する。
