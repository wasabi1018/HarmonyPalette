作成日：2026-10-18（日本時間）
状態：Webページ・管理画面・計算・気象庁XML取得・保存と定期処理を2026-10-18に実装。ローカル検証済み。本番DBへの適用・デプロイは未実施。係数はユーザー指定の初期仮説であり、実際の混雑に対する精度は未検証。実装入口と確定事項は `knowledge/specs/混雑予想ページ.md` を参照。

追記方針：天気データは無料取得を必須条件とし、気象庁の公開XMLを第一候補とする。ユーザーの現地知見に基づき、キャラクターごとの誕生日による混雑への影響を独立した主要要因に追加する。

更新運用：天気の自動取得と予想カレンダーの定時更新は毎日19時（日本時間）に1回行い、対象は翌日以降だけとする。当日分は定時更新で書き換えない。閲覧時は保存済みの結果を表示し、ページ表示・再読み込み・日付切替を気象庁へのアクセスや混雑度の再計算のきっかけにしない。

最新指定：実際の混雑を記録する管理フォームは設けない。誕生日だけ天気の影響を弱める扱いも設けず、全体に共通の天気係数を使う。予定の未公開状態をカレンダーに明記し、予報がある日には天気アイコンを表示する。当月内の過ぎた日は当時公開した予想を保持して設定変更で上書きせず、過去月の混雑予想は表示・保存しない。

カレンダーの見た目は現行のInstagram用カレンダーを基準とする。「ファンスタ3部屋」は、1日の使用部屋が3部屋あり、かつ重複を除いた1日のグリーティング枠数が通常の平日より多い場合に表示する。午前・午後の部屋の切り替えだけで3部屋になり、枠数は通常どおりの日には表示しない。

## 提案の要点

「曜日・連休・季節・イベントから求める基本予想」に、「直近の天気補正」「キャラクター別の誕生日補正」「営業体制補正」を加える。ユーザーの指定に基づき、営業時間の加点を誕生日の加点より大きくする。公開表示は園内全体の日単位の混雑傾向とし、実際の入園者数や個別施設の待ち時間の推計とは分ける。

ファンスタの回数や長時間営業は、運営側の需要予測を反映する可能性がある一方、受け入れ能力も表す。ファンスタは最大5点、営業時間は7時間で0点・10時間で30点・11時間以上で40点を初期値として試算する。この重み付けはユーザーの優先度を反映する仮設定で、管理画面から調整できるようにする。実際の混雑を収集・記録する機能は含めない。

添付画像からは、曜日、連休、学校休暇、イベントの節目、割引施策、天気などの要因の考え方を参考にする。画像内のディズニー向け人数加算・収容人数・天気係数をハーモニーランドに転用しない。前年同日の天気を未来の予報として表示する方式も採らない。

## 現在の実装から利用できるもの

- `lib/crowd-calendar.ts` に混雑区分、月別手動設定、イベント期間、表示情報の集計がある。現在の区分は「普通・混雑・大混雑」の3段階。
- ファンスタは確認済み予定から異なる部屋番号を集計している。現在の「3部屋」は、1日の開催回数ではない。現行実装は部屋番号が3種類あるかだけで自動表示を判定しており、通常の平日より枠数が多いかという新条件は未実装。
- ファンスタ予定には日付・部屋・開始時刻・終了時刻があり、枠数と開催時間を集計できる。同じ部屋・日付・開始時刻を同一枠として扱う既存の識別方法がある。
- 営業情報には営業／休園／不明、開園・閉園時刻がある。現在の画像用「ナイト営業」は閉園が17時を超える日を示す。
- 季節イベントは開始・終了日を管理しているため、最初・最後の土日の算出を追加できる。ただし各日開催する通常のショーから季節イベントを自動判定しない。
- `/daily-schedule` とトップの日別予定は `components/home-today-sections.tsx` を利用する。日付選択に合わせて天気・混雑度を切り替える場所として適している。
- `/schedule` の日付詳細ダイアログは `components/schedule-browser.tsx`。同じ日別情報を共有できる。
- 現行のInstagramカレンダーは非公開の手動下書き。Web公開用のイベント・手動補正には、別途公開対象を確定する仕組みが必要。

## 計算式の仮案

```text
連休補正     = max(0, 連休日数による加点 - 初日減点 - 最終日減点)
暦補正       = min(25, 連休補正 + 学校休暇補正)
営業体制補正 = max(ファンスタ補正, 営業時間補正)  // 初期設定では最大40点
基本スコア   = 曜日基準 + 暦補正 + イベント補正 + 営業体制補正 + 特別日補正
天気係数     = 1 + 予報日数に応じた反映率 × (天気の基本係数 - 1)
誕生日補正   = 対象キャラクターに設定した誕生日の加点（重複日は最大値）
自動スコア   = round(clamp((基本スコア + 誕生日補正) × 天気係数, 0, 100))
```

内部スコアは比較・調整のために保持し、点数・計算式・加点内訳・係数・混雑区分の数値境界は管理画面だけに表示する。公開画面には混雑区分と主な理由、算出に使う要素の概要を表示し、具体的な算出方法は掲載しない。公開カレンダーの日付マスの混雑表示は色分けのみとし、日付の下にイベント・ファンスタ3部屋などのトピックスを併記できる。設定変更前後の違いは管理用プレビューで確認できるようにする。

特別日補正は、日付別に登録する加点・減点。未設定時は0点で、通常の天気補正の対象にする。最終区分を手動指定した日は、その区分を優先し、自動スコアは検証用の参考値として残す。

### 曜日・暦の仮値

| 要因 | 仮値 | 適用方法 |
| --- | --- | --- |
| 土日祝の前日・翌日に当たる平日 | 30点 | 曜日基準。通常平日25点に加算する方式ではない |
| その他の平日 | 25点 | 基準 |
| 土曜 | 60点 | 基準 |
| 日曜 | 55点 | 基準 |
| 祝日・振替休日 | 60点 | 曜日基準を置き換える。土曜＋祝日の二重加算はしない |
| 2連休以下 | 0点 | 通常の土日の加点は曜日基準に含める |
| 3連休 | ＋8点 | 連休の全日に適用 |
| 4連休 | ＋12点 | 連休の全日に適用 |
| 5連休 | ＋16点 | 連休の全日に適用 |
| 6連休以上 | ＋20点 | 連休の全日に適用する初期上限 |
| 3連休以上の初日 | −5点 | 日数別の連休加点から差し引く仮の初期値 |
| 3連休以上の最終日 | −5点 | 日数別の連休加点から差し引く仮の初期値 |
| 学校の長期休暇 | ＋5点 | まずは登録した地域・学校区分の期間で扱う。全国一律の日程とみなさない |

土日祝前後の平日は、平日自身が祝日ではなく、その前日または翌日が土曜・日曜・日本の祝日等に当たる日とする。通常は月曜・金曜に加え、平日の祝日の前日・翌日も対象になる。前後の両方が該当しても曜日基準は30点で、二重に加算しない。祝日自身は祝日基準を使う。ユーザーへの確認により「＋30点」は曜日基準30点の意味と確定し、通常平日25点に30点を加える方式にはしない。

ユーザーの指定に基づき、連休加点は連休全体の日数で切り替える。上記の点数は検証用の初期値で、管理画面から日数別に編集できる。

連休は、土日と日本の祝日・振替休日・祝日に挟まれた休日からなる、切れ目のない休日のまとまりとして数える。対象月の前後も確認し、月をまたぐ連休を月境界で分断しない。5連休なら全日を＋16点の基礎加点とし、ユーザーの指定に基づき、初日と最終日はそれぞれ5点を差し引いて実質＋11点、中日は＋16点にする。残り日数で加点を減らしたり、3連休分と4連休分を積み上げたりしない。連続営業日数とは別で、連休中の休園日は混雑度を出さず休園表示を優先する。

初日減点と最終日減点は別設定にし、初期値はどちらも5点。3連休以上だけに適用し、通常の土日など2連休以下には付けない。減点後の連休補正は0点を下限とし、連休加点を超える減点によって通常の曜日基準を引き下げない。休日のまとまりの初日・最終日を使い、休園を理由に最初・最後の営業日へ減点を移さない。減点は暦補正の計算時に行い、天気補正と表示スコアの上限100点を適用する前に反映する。

GW・お盆・年末年始で平日を含む特別な休暇期間を使う場合は、確認した期間を別途登録する。自動判定の連休と同じ休日需要を二重加算しない。飛び石の平日は、自動で前後の連休をつなげず、必要に応じて管理者が理由付きで補正する。

連休補正の最大20点と学校休暇補正5点を反映できるよう、暦補正の初期上限を15点から25点に変更する。連休翌日、地域限定の休校日、団体来園、割引施策は、確認できた日に管理者が理由を付けて補正する。画像にある「連休翌日＋5,000人」などはそのまま移さない。

### イベント補正の仮値

| イベントとの関係 | 仮値 |
| --- | --- |
| 通常の開催期間中 | 0点 |
| 初日・最終日 | ＋12点 |
| 最初の土日・最後の土日 | ＋10点 |

ユーザーの指定に基づき、「ハロウィーン開催期間中」など通常のイベント開催期間であることを理由にした一律加点は行わない。初日・最終日・最初と最後の土日という節目の加点は維持する。イベント名や開催情報の表示は引き続き行える。

- 同一イベント内では最大値だけを使う。土曜の初日は＋12点とし、＋12＋10にはしない。
- 複数イベントが重なる日も、初期版では最も大きい補正だけを採用する。大型イベントの個別調整を含めても最大15点とする。
- 最初・最後の土日は「イベント期間と重なる、最初・最後の土日ペア」と定義する。日曜開始ならその日曜、土曜終了ならその土曜も対象とする。対象はイベント期間内の日だけ。
- 短いイベントで最初と最後の土日が同じでも二重加算しない。
- 期間初日が休園日の場合は休園を優先する。初営業日を特別扱いしたい場合は、管理者が明示的に設定する。
- 誕生日は以下の専用補正で扱う。誕生日のお祝いイベントをイベント補正にも登録した場合は、同じ集客要因を重複加算せず大きい方だけを使う。独立した季節イベントとの重なりは別要因として記録し、調整対象にする。
- 限定グッズ発売、特別出演などは情報タグとして表示できるが、誕生日や季節イベントと同じ理由の加点を増やさない。

### キャラクター別の誕生日補正

ユーザーから、クロミのような人気キャラの誕生日はかなり混み、通常の混雑と変わらないキャラもいるとの現地知見が提示された。誕生日を全キャラ共通の加点にせず、キャラクターごとに「誕生日の混雑への影響」を管理する。これはハーモニーランドでの集客への影響であり、一般的な人気投票順位をそのまま係数にしない。

| 管理上の影響区分 | 仮の加点 | 初期設定の考え方 |
| --- | --- | --- |
| 通常どおり | 0点 | ユーザーが通常どおりと確認したキャラ |
| 小さい | ＋5点 | 今後、現地知見に基づき設定 |
| 大きい | ＋10点 | クロミをユーザーの知見に基づく初期候補とする |

数値は検証前の仮値であり、その他のキャラを推測で区分しない。未設定と「影響なし・0点」は区別する。未設定は暫定加点0点として、管理画面に「誕生日の影響未評価」を表示する。

- 既存キャラクターマスターにあるID・誕生日の月日を参照し、混雑用の加点と判断メモを別設定として持つ。表示順や画像、紹介文の順位から推定しない。
- 誕生日当日に適用する。実際のお祝い・特別出演日が異なる場合は、その対象日と加点を別途指定できるようにする。前後の土日や月全体を一律に加点しない。
- 誕生日が重なった場合は初期版では最大値のみ。複数キャラによる追加の影響を反映したい場合は、日付単位の管理者調整で対応する。
- 当日の出演予定が未発表でも、誕生日という事実と既知の集客への影響は利用する。「出演未発表＝誕生日加点0」にはしない。確認済みの特別出演や中止を別情報として記録する。
- 園内全体の混雑区分と、該当キャラのファンスタ・グリーティングへの集中を分けて説明する。公開表示には「クロミの誕生日」のような理由を出し、キャラの人気順位表は出さない。

ユーザーの最新指定に基づき、誕生日加点を0・5・10点の3段階にする。「通常どおり・小さい・大きい」で管理する。晴れ・他の補正なしなら、土日祝前後ではない平日25＋クロミ誕生日10＝35点「普通」、土曜60＋10＝70点「混雑」。誕生日補正0点のキャラなら、その日の通常の予想を維持する。これは管理用の計算例で、公開ページには掲載しない。

誕生日だけ雨の影響を弱める扱いは、ユーザー指定により採用しない。基本スコアと誕生日補正を合算してから、全体に同じ天気係数を1回だけ掛ける。誕生日専用の天気感応度・係数の設定欄は設けない。

### ファンスタ・営業時間補正の検証候補

ファンスタは日付・正規化した部屋名・開始時刻で重複排除し、複数キャラクターの登場を複数枠として数えない。公開・確認済み予定のみ利用する。未発表や取り込み漏れを「開催0回」として扱わない。

| 要因 | 検証用の仮値 | 留意点 |
| --- | --- | --- |
| 営業1時間当たりの枠数が比較基準の1.2倍以上 | ＋3点 | 営業時間が長いために総回数だけ増える影響を抑える |
| 同1.5倍以上 | ＋5点 | 1.2倍の補正とは重複させない |
| 7時間営業（8時間未満） | 0点 | 通常営業の基準。短縮営業でも自動減点しない |
| 8時間以上9時間未満 | ＋10点 | 時間別設定の補間となる初期値 |
| 9時間以上10時間未満 | ＋20点 | 誕生日加点の初期最大値＋10点より大きい |
| 10時間以上11時間未満 | ＋30点 | 10時間営業の初期値 |
| 11時間以上 | ＋40点 | 11時間営業の初期値・営業時間補正の初期上限 |

ファンスタの比較基準は、公開・確認済み情報が揃った直前8週間の同じ曜日・祝日区分の中央値を候補とし、比較できる日が4日未満ならファンスタ補正を付けない。営業時刻が欠ける日には時間当たり枠数を計算しない。

7時間・10時間・11時間営業で加点を変えたいというユーザーの指定に基づき、営業時間補正を段階制にする。初期値は7時間営業0点、8時間営業10点、9時間営業20点、10時間営業30点、11時間以上40点とする。祝日の比較データが不足していても、確認済みの開園・閉園時刻の差から判定する。休園日・営業時刻不明の日には加点しない。時間帯の境界と加点は管理画面から編集できる。

時刻は分単位で計算し、最も大きい適合条件の加点だけを使う。例えば9時間30分は＋20点、10時間30分は＋30点。四捨五入で上の時間帯へ繰り上げたり、時間帯ごとの加点を累積したりしない。7時間未満も初期値0点とする。

誕生日より営業時間を強く評価する方針は、9時間以上の営業に適用する。「9時間以上の各段階の営業時間加点 ＞ 有効な誕生日加点の最大値」を設定値で検証し、初期値は20・30・40点のいずれも誕生日の最大10点を上回る。7時間は通常営業、8時間は小幅な延長として扱う。営業体制補正の上限は初期値40点とし、設定した営業時間加点を切り下げる上限は保存できないようにする。天気係数は営業時間分・誕生日分に共通で適用する。

枠数と営業時間の補正は最大値だけを使用する。「3部屋」と枠数も同じ体制を表すため二重加算しない。開催回数の減少や短縮営業による自動減点は、少ない受け入れ枠に人が集中する可能性を評価できるまで導入しない。

上記の補正を初期の計算仕様として管理用プレビューで確認し、必要に応じて設定を調整する。ファンスタの予約の取りにくさを示す別指標は今回の範囲に含めない。

### 「ファンスタ3部屋」の表示条件

ユーザーの指定に基づき、公開カレンダーの「ファンスタ3部屋」の自動表示は次の両方を満たす場合に限る。

1. 公開・確認済みのファンスタ予定で、その日に使用する異なる部屋番号が3つある。
2. 重複を除いた1日のグリーティング枠数が、2026年10月19日の確認済み予定を基準とする22枠を上回る。

枠数は前述の日付・正規化した部屋名・開始時刻で数え、同じ枠に複数キャラクターが出演しても1枠とする。表示の比較に使うのは1日の総枠数であり、混雑スコア用の「営業時間当たりの枠数」や1.2倍・1.5倍の条件とは分ける。使用部屋が3つという事実だけで混雑点を追加しない。

例えば、101号室は終日使い、もう1室を午前は102号室、午後は103号室へ切り替える場合、1日の部屋番号は3種類になる。この場合でも総枠数が通常の平日と同じなら「ファンスタ3部屋」は表示しない。3部屋の同時使用を新たな必須条件にはせず、使用部屋数と総枠数で判定する。

ユーザー指定の基準日である2026年10月19日は、公開・確認済みデータを2026年10月18日に読み取りで再確認したところ、101号室11枠・102号室11枠の合計22枠だった。これを表示判定の初期基準として固定する。比較例は次のとおり。

| 使用する部屋 | 1日の枠数（通常の平日の基準は22枠） | 表示 |
| --- | --- | --- |
| 3部屋 | 22枠・通常と同じ | 非表示 |
| 3部屋 | 33枠・通常より多い | ファンスタ3部屋 |
| 2部屋 | 33枠・通常より多い | 非表示 |

「通常の平日の枠数」の初期値は22枠、基準日は2026年10月19日とし、管理画面に根拠として表示する。参照元の予定が後から更新されても基準値を自動変更せず、変更する場合は管理者が明示的に保存する。対象日の予定が未公開・欠損と判明している場合は、自動表示の条件を満たしたとは扱わず管理画面に「判定保留」、公開カレンダーに該当する未公開・確認中の状態を示す。取り込み件数が少ないことだけから実際の開催数が少ないと断定しない。

この判定は毎日19時の定時処理、または管理者が設定を保存したときに行い、公開側には保存済みの表示フラグを渡す。閲覧時の再集計は行わない。現行Instagram編集画面の手動表示は、確認済みの3部屋使用と通常より多い枠数を管理者が確認した場合の補正として扱い、単なる部屋の切り替え日を表示対象にはしない。既存の保存済み下書きは自動で書き換えない。

### 10月19日の天気を仮定した試算

2026年10月19日（月）は、公開・確認済み情報では10:00〜17:00の7時間営業、ファンスタ2部屋・22枠で比較基準と同程度、登録上の誕生日該当なし。3連休以上の対象でもイベントの節目でもない。日曜の翌日の平日に該当するため、曜日基準は30点となる。平日すべてを30点とする旧ルールによるものではない。

- 晴れ・曇りで降雨の影響が小さい場合：30×1.00＝30点・普通。
- 一時雨の場合：round(30×0.95)＝29点・普通。
- 雨と晴れ・曇りが混在する場合：30×0.90＝27点・普通。
- 雨が主体の場合：30×0.80＝24点・ゆったり。
- 営業時間中に大雨が長く続く場合：round(30×0.65)＝20点・ゆったり。

これは実際の天気予報を確定した結果ではなく、天気を仮定した管理用の条件付き試算。

## 天気補正

無料の気象庁データで取得できる天気・時間帯別の降水確率・地域時系列予報を使う。当日〜翌日は提供される時間帯と営業時間の重なりを確認し、それ以降は日単位の情報を使う。日単位の雨予報しかない日に、営業時間の半分が雨だったなどと推定しない。

| 取得した予報の内容 | 基本係数の例 |
| --- | --- |
| 晴れ・曇りで降雨の影響が小さい | 1.00 |
| 晴れ・曇りに一時雨など | 0.95 |
| 雨と晴れ・曇りが混在 | 0.90 |
| 雨が主体 | 0.80 |
| 営業時間中に大雨が長く続くと確認できる場合 | 0.65 |

「雨なら0.5」は初期設定としては強すぎる可能性がある。人数が半分になると確認できていないため、弱い補正から検証する。雨天時は屋内やファンスタに人が集中する可能性もあり、園内全体の予想が下がっても個別施設が空くとは表示しない。

大雨の区分を検討案に追加し、通常の雨0.80と分けて仮係数0.65を用意する。これは混雑予想のための未検証の係数で、来園者数が必ず65％になるという意味ではない。通常の雨の係数と重ねて掛けず、大雨の条件が確認できる場合は0.65だけを使う。夜間だけの大雨を昼間の営業に一律適用しない。

降水確率は雨の強さや降る時間の割合ではない。降水確率80％を「営業時間の80％が雨」や「強い雨」と解釈しない。提供されていない時間降水量・強雨の継続時間は推定せず、天気コード・時間帯の分類規則を公開前に固定する。欠損値は0に置き換えない。

大雨補正の自動適用は、取得した予報で対象地域・時間帯・強い雨の継続を確認できる場合に限る。無料で取得する予報だけでは判定できない場合は通常の雨の分類を使い、降水確率100％や警報の存在だけから終日の大雨と決めない。管理者が別資料で確認して大雨補正を指定する場合は根拠と対象時間を記録し、「管理者補正」として扱う。気象庁が発表した天気や降水確率の表示そのものは書き換えない。

参考：[気象庁の降水確率の説明](https://www.jma.go.jp/jma/kishou/know/kurashi/yoho.html)。

### 予報日数による反映率

日数は日本時間で対象日と計算日の日付差を求める。

| 対象日までの日数 | 天気の反映率 | 表示 |
| --- | --- | --- |
| 当日〜2日後 | 1.0 | 天気を反映した予想 |
| 3〜6日後 | 0.5 | 天気を弱めて反映した予想 |
| 7日後以降 | 0 | 暦・イベントを中心とした基本予想 |

これは精度保証ではなく、遠い予報の影響を抑える運用上の仮案。天気データを取得できても7日後以降は混雑計算に使わない。週間予報は発表日の翌日から7日先まであり、取得日から必ず7日分あるとは限らない。取得時刻を変更した場合や配信が遅れた場合も、対象日を実際の予報期間と照合する。7日後の天気も取得済み電文の対象なら「参考予報」として表示でき、対象外の日に前の予報を流用しない。「予報対象外」と「天気を取得できません」は区別する。3日目以降に気象庁の信頼度A〜Cがある場合は原情報として表示し、独自の混雑予想の信頼度と混同しない。

台風・荒天から休園を自動推測しない。公開・確認済みの営業情報で休園と判明した日は混雑予想を置き換えて「休園日」とする。

### 計算例

土曜日60点＋イベント最初の土日10点＋営業体制5点＝基本75点。

- 晴れなら75点 → 「混雑」
- 当日〜2日後の、雨主体の予報なら75×0.80＝60点 → 「やや混雑」
- 同じ雨予報でも3〜6日後なら、係数1＋0.5×(0.80−1)＝0.90、75×0.90≒68点 → 「やや混雑」
- 天気未取得・予報対象外なら基本75点から「混雑」と判定し、「天気未反映」と明示。公開画面に点数は出さない

いずれも管理用の仮の入力による例で、実際の日付の予想ではない。公開ページの説明には計算例を掲載しない。

## 混雑区分・手動補正・情報不足

ユーザーの最新指定に基づき、内部スコアを次の5段階へ変換する。「ゆったり」と「普通」の境界は従来の25点を維持する。この数値表は管理用であり、Web公開時は区分名と色の凡例だけを掲載する。

| スコア | 表示 |
| --- | --- |
| 0〜24 | ゆったり |
| 25〜49 | 普通 |
| 50〜69 | やや混雑 |
| 70〜89 | 混雑 |
| 90〜100 | 大混雑 |

「休園日」「基本予想」「予想できる情報が不足」は混雑区分と別の状態として扱う。営業情報が不明な日は、開園を保証せず「営業情報未確認・基本予想」と表示する。天気やファンスタが未発表でも暦による基本予想は出せるが、欠けている補正があることを表示する。

通常の公演スケジュールとファンスタスケジュールは、日付ごとの公開状況を別々に持つ。未公開と確認できる日には、それぞれ「スケジュール未公開」「ファンスタスケジュール未公開」を公開カレンダーと日別詳細に明記する。両方未公開なら両方を表示する。未公開の要因を0回・開催なし・補正なしと同じ確定情報として説明せず、その要因が未反映の基本予想であることを示す。

予定データが0件というだけで未公開と断定しない。公開元の公開状況を確認した情報と、登録済み予定の有無を区別する。取り込み待ち・確認できない状態は「スケジュール確認中」「ファンスタスケジュール確認中」、取得障害は更新遅延として扱い、未公開と混同しない。確認済み休園日は休園表示を優先する。

優先順位は、確認済み休園 ＞ 管理者が指定した最終区分 ＞ 自動予想。手動指定には対象日・理由・更新日時を持たせる。手動指定後も自動スコアは検証用に残し、手動区分から架空の点数を逆算しない。手動区分は天気更新では動かさず、表示上も「管理者による調整」と分かるようにする。

Instagramの既存3段階を続ける場合、自動予想から画像を新規作成するときの内部対応は0〜69点＝普通、70〜89点＝混雑、90点以上＝大混雑を候補とする。画像にも点数は載せない。保存済みの手動下書きを自動で置き換えない。Webと画像は更新時点・判定方式が異なることを示す。

## 無料の天気データ：気象庁を第一候補に変更

無料取得を必須条件とする。第一候補は、気象庁が自動処理向けに公開している防災情報XMLのPULL型配信。ユーザー登録は不要で、XML電文は商用利用も可能と公式に説明されている。有料の確実な配信サービスとは区別する。Open-Meteoの有料プランを前提とした初案を、この方針に置き換える。

| 取得対象 | 利用する情報 | 範囲・粒度 |
| --- | --- | --- |
| 府県天気予報／地域時系列予報 | 天気、6時間単位の降水確率、最高・最低気温、3時間単位の天気等 | 府県天気予報は今日・明日・明後日。時間帯別の確率や気温等は項目ごとに提供期間が違う |
| 府県週間天気予報 | 天気、降水確率、最高・最低気温、降水予報の信頼度 | 翌日から7日先。短期予報とは対象区域・地点が異なる場合がある |

日出町の短期予報の対象は「大分県中部」。週間予報は原則として「大分県」の情報なので、両者を区別して表示する。気温は各予報に含まれる予報地点の数値であり、ハーモニーランド園内の観測値・ピンポイント予報と称さない。近くの地点を距離だけで選び、予報対象区域を取り違えない。

### 取得方法と運用

- 公式PULL型ページから定時の長期Atomフィードを取得し、必要な大分県の天気予報・週間予報の電文だけを読む。長期フィードは毎時更新で数日間の入電を掲載しており、1日1回取得する運用に使う。高頻度フィードは掲載窓が短く必要な電文を見逃すため、この運用には使わない。
- 府県天気予報の定時発表は5・11・17時、週間予報は11・17時ごろ。19時に、その日17時発表分など取得時点の最新の有効な予報を使う。19時以降の修正や翌朝5時・11時の予報変更は、翌日19時の定時処理まで取り込まない。
- サーバーの定期処理だけが気象庁へアクセスし、天気と計算済みの日別予想をデータベースへ保存する。閲覧者ごとのアクセス、再読み込み、日付切替、キャッシュ切れを理由とした外部取得は行わない。取得済み電文のURLを記録し、同じファイルを繰り返しダウンロードしない。
- 発表日時、取得日時、対象日、地域、気温地点、時間区分、情報不足を分けて保持する。訂正・取消・訓練情報等も判別し、通常の最新予報だけを表示する。
- 更新の成否は「最新の取得成功時刻」だけでなく、予報の発表日時と有効期間で判定する。同じ古い予報を再取得して新しい予報とみなさない。取得に失敗した場合は有効なキャッシュを更新遅延表示で使い、有効期間を外れた情報は表示・補正から除外する。
- 表示例：「出典：気象庁」「気象庁予報をもとにHarmony Paletteが混雑予想を作成」。予報の天気・降水確率自体を独自の数値に書き換えない。気象庁による混雑予想と誤解させない。

### 毎日19時に更新する処理

更新時刻は毎日19時（Asia/Tokyo）、定時更新の対象は翌日以降とする。当日分の混雑度・天気・トピックスは定時更新で書き換えず、前日に保存した内容を使う。19時と翌午前1時は通常どちらも同じ17時発表分を使うが、19時なら夜の来園計画に早く反映できる。長期フィードの毎時更新に対し、17時の発表から時間を置ける点も運用上の余裕になる。ただし、19時までに必ず新しい電文が掲載される保証としては扱わない。これはWebサービス側の定期処理の設計であり、このチャットのリマインダーやローカルPCを起動しておく運用にはしない。

1. その日の更新処理をサーバーのスケジューラーから起動する。日本時間の日付を実行単位とし、同日の二重起動・同時実行を防ぐ。
2. 長期Atomフィードと必要な予報電文を取得し、対象地域・発表時刻・予報対象日を確認して、翌日以降の表示に使う天気データを保存する。「1日1回」は更新処理の頻度であり、天気予報と週間予報など複数の必要ファイルの取得は同じ処理内で行う。
3. 公開カレンダーの対象期間のうち翌日以降について、保存済みの営業情報・ファンスタ予定・イベント・誕生日・適用中設定から混雑度を計算する。スケジュールとファンスタの公開状況、3部屋表示、天気アイコンも日別に保存する。天気はその電文の予報対象日にだけ反映し、期間外の日も暦などから基本予想を作る。日数による反映率は、この処理を行う日本時間の日付を基準にする。
4. 天気未反映の基本予想も保存し、予報が無効になった場合に閲覧時の再計算なしで利用できるようにする。翌日以降の天気と日別結果が揃った予想セットを保存後、公開ページが読むセットを一括で切り替える。当日分と当月内の過去日はそのまま引き継ぎ、設定変更で過去の予想を再計算しない。
5. 公開カレンダー、日別スケジュール、トップの今日の予定は同じ保存結果を読む。公開表示用のキャッシュを使う場合は、この保存時に更新する。閲覧時のキャッシュ更新処理にも気象庁へのアクセスや混雑度の計算を含めない。

取得に失敗した場合は、有効な保存済み予報を「更新遅延」と分かる表示で使う。有効期限を過ぎた天気は表示・補正に使わず、保存済みの基本予想を「天気未反映」として表示する。予想セットの計算・保存に失敗した場合は前回のセットを維持し、公開結果が途中まで更新された状態を避ける。ページ閲覧を失敗時の再取得のきっかけにせず、次回の定時処理で再取得する。実行結果・最終成功時刻・失敗内容は管理画面で確認できるようにする。

管理者が設定・日付補正を明示的に保存した場合は、既に保存してある天気を使って予想を更新できるものとする。この操作でも気象庁から天気を取り直さない。確認済みの休園情報は常に優先し、定時更新待ちを理由に営業日の混雑予想を表示し続けない。

当月内の過去日は、当時公開した混雑予想・天気アイコン・公開状況・版を保持し、設定保存・復元・再計算でも上書きしない。当月のカレンダーからは当時の予想として閲覧できる。過去日の詳細では天気も「当時の予報」と明示し、実測天気として表示しない。有効期間外の天気を当日・未来の予報に使わない規則と、この過去日の表示は区別する。過去月のカレンダーへの移動・直接URL・公開APIによる混雑予想の取得は提供せず、過去月の日別混雑予想データは保存しない。実績比較用のアーカイブや履歴分析データも設けない。

月が変わったら日本時間の当月を基準に公開可能な最小月を切り替え、過去月の混雑予想を直ちに表示対象から外す。過去月の日別予想・予想の旧版・その表示だけのために保存した天気データは、月初のサーバー側の削除処理で除去し、閲覧を削除や再計算のきっかけにしない。月初の削除処理は気象庁へアクセスせず、1日1回の天気取得とは別の保存期間管理とする。削除に失敗しても公開範囲は当月以降に制限し、管理画面に失敗を示す。設定の変更履歴・基準日2026年10月19日の22枠という設定根拠は引き続き保持する。元のスケジュール台帳・営業情報・既存のInstagram用手動下書きや出力画像を削除する要件ではない。

気象庁サイトの表示用JSONを利用する方式も見かけるが、公式に仕様案内のあるXMLと同じ外部向けAPI契約として扱わない。今回は公式公開のXMLを優先し、JSONに依存する場合の形式変更対応は別途判断する。

## ページ・スケジュール上部の構成

新規ページのURL候補は `/crowd-forecast`。主役は月別カレンダーとし、直近7日を比較できる一覧を添える。日付を選ぶと、営業時間、営業中の天気、混雑区分、予想の理由、当日のスケジュールへのリンクを表示する。

カレンダーの見た目は現行のInstagram用デザインに合わせる。ブランド表記、年月見出し、淡いピンクの背景・枠線、丸みのある7列の日付マス、上部の色の凡例、休園日の灰色の斜線、日付下の短いトピックスを基準とする。参照元は `components/admin/instagram-crowd-calendar-studio.tsx` の `CrowdCalendarCard` と、`output/instagram/crowd-calendar-2026-10/harmony-palette-crowd-calendar-2026-10.png`。既存3段階の色合いを土台に、Webの5段階を区別できる配色へ拡張する。画像の1080×1350pxをそのまま縮小表示する方式を前提にせず、Webではスマートフォンでも日付とトピックスが読めるよう余白・文字サイズを調整し、日付を押すと詳細を開けるようにする。

PCの画面構成は、ユーザーが選んだ生成案②を視覚目標とする。左に月別カレンダー、右に選択日の混雑区分・天気・最高最低気温・降水確率・営業時間・スケジュールへの導線を置く。[選択済みのPC参照画像](../output/crowd-forecast-design-2026-10-18/desktop-selected.png)をプロジェクト内に保存した。この画像内の日付マスにある未公開の文言は、下記の最新指定でカレンダー上部へ移す。参照画像で省略されている最高最低気温・降水確率は日別詳細へ追加する。

スマートフォンの通常画面は、上から見出し・更新案内、未公開のお知らせ、月送り・凡例、月別カレンダー、算出要素の概要という順にする。PCの右側にある日別詳細は、スマートフォンでは日付をタップしたときのモーダルにする。カレンダーの下へ日別詳細を常設しない。7列のカレンダーを維持し、日付・天気を優先する。トピックスは短い表記やアイコンを使い、正式名称と全内容は選択日のモーダルで確認できるようにする。

スマートフォンの日別モーダルは、画面下から開くボトムシート型を基本にする。選択した日付、混雑区分、天気、最高最低気温、降水確率、営業時間、ファンスタなどのトピックス・公開状況、当日のスケジュールへのボタンを表示する。背景を薄く暗くし、開いている間は背景の操作・スクロールを止める。右上の閉じるボタン、背景タップ、Escapeキーで閉じられるようにし、閉じたら元の日付とスクロール位置へ戻す。長い内容はモーダル内だけをスクロールし、表示領域の高さを超えないようにする。ダイアログの読み上げ名を日付にし、フォーカスをモーダル内に保って閉じたら元の日付へ戻す。PCの日別詳細は右側表示を維持する。

[スマートフォン最新版の画面イメージ](../output/crowd-forecast-design-2026-10-18/mobile-weather-v3.png)と[生成条件](../output/crowd-forecast-design-2026-10-18/README.md)を保存した。絵文字を使わないお知らせ欄と、最高最低気温・時間帯別降水確率を含むボトムシート型モーダルを示す検討用画像であり、スマートフォン版の最終承認や画面実装を意味しない。旧案 `mobile.png` と `mobile-modal-v2.png` は変更前の参照として残す。最新版は10/18の19時更新後に翌日10/19の予報を表示するサンプルで、画像内の天気・気温・降水確率は実際の予報ではない。

公開カレンダーの日付マスには日付を表示し、混雑度は色分けだけで示す。点数・加点内訳・数式は表示せず、日付マス内の混雑区分名も省く。日付下には、イベントの開始・最終日、条件を満たす日の「ファンスタ3部屋」、ナイト営業、キャラクターの誕生日などを既存デザイン同様に併記できる。「混雑度は色分けのみ」はこれらのトピックスを非表示にする意味ではない。近くに5段階の「色と区分名」の凡例を置き、選択した日の詳細では区分名を表示する。読み上げ用の日付ラベルにも区分名を含めるが、点数は含めない。休園・情報不足の状態は混雑の色と区別し、休園を「ゆったり」として扱わない。

各日付マスの右上など、日付と重ならない位置に天気アイコンを表示する。晴れ・曇り・雨・混合天気など、保存した予報の天気コードに対応するアイコンを使う。日別詳細では元の天気の文言と気象庁の発表日時も確認できるようにする。大雨の専用アイコンは、取得した天気情報でその内容を確認できる場合だけ使い、降水確率や管理者の混雑補正だけから作らない。

予報対象外の日は天気を推測せず「—」とし、凡例や詳細で「天気予報対象外」と分かるようにする。取得失敗で使える予報がない場合は「天気未取得」と区別する。前年同日や通常の季節天気のアイコンを未来の予報として表示しない。アイコンの読み上げ用ラベルにも天気の文言を付け、公開カレンダーとスケジュール上部で同じ保存済み予報を使う。日付切替や日付を押す操作で天気を取り直さない。

日別の天気情報は、天気の文言とアイコンに加え、最高気温・最低気温・降水確率を提供される範囲で必須表示とする。表示場所はPCの右側詳細、スマートフォンの日別モーダル、1日のスケジュール上部の天気カード。カレンダーの日付マスは天気アイコンを基本とし、降水確率の数値を追加して文字を詰め込まない。

短期予報の6時間ごとの降水確率がある場合は、元の時間区分を添えて表示する。10:00〜17:00営業なら「6〜12時 20％」「12〜18時 30％」のように、営業時間と重なる区分を優先する。閉園が18時以降なら18〜24時の区分も対象にし、値は元のまま表示する。この例の数値は画面説明用のサンプルである。「営業時間中の降水確率」や「1日の降水確率」として時間帯の値を最大値・平均値にまとめない。

週間予報の日単位の降水確率だけがある日は「降水確率 40％（日単位）」のように表示し、6時間単位の値を補完しない。短期の降水確率・気温がどの日まで取得できるかは、取得日ではなく予報の発表日と対象時刻で判定する。19時の更新では、その日に発表された翌日の6時間区分を翌日分へ保存する。気温と降水確率の欠損は0℃・0％へ置き換えず、予報なし・未取得を区別する。

風向・風の強さや週間予報の信頼度A〜Cも取得候補だが、初期画面の優先表示は天気・最高最低気温・降水確率とする。A〜Cは降水予報の信頼度であり、混雑予想の的中率として表示しない。天気情報の出典・地域・気温地点・発表日時は日別詳細で確認できるようにする。

「スケジュール未公開」「ファンスタスケジュール未公開」の案内文は、PC・スマートフォンともカレンダー上部のお知らせ欄にまとめる。警告の絵文字は使わず、淡いピンクの背景・細い枠線・既存UIと同じ線画の注意アイコンを使い、見出し「スケジュール公開状況」を添える。アイコンはピンク系の円内に感嘆符を描いた線画など、サイトのアイコンと線幅・色を合わせた表記にし、黄色い絵文字の警告マークにはしない。状態は文言でも説明し、色やアイコンだけで意味を伝えない。

日付マス内には未公開の文を表示しない。対象月全体が未公開なら月単位、一部の日だけなら日付・連続する期間をまとめて示し、どの日に該当するか分かるようにする。公演とファンスタの案内は区別し、両方が未公開なら両方を掲載する。選択した日の詳細でも公開状況は確認できるものとする。

画面イメージ用の文案例：

- スケジュール未公開：10/27
- ファンスタスケジュール未公開：10/26

日付は説明用のサンプルであり、実際の公開状況を示すものではない。案内文が長い場合は上部欄で自然に折り返し、横スクロールや日付マスへの重複表示は行わない。月を切り替えたら、表示月の保存済み公開状況に合わせてお知らせも切り替える。

ページ内に「混雑予想について」の概要説明を掲載する。使う要因と予想の性質を文章で説明し、基準点、加点・減点、係数、数値境界、具体的な計算式・計算例は公開しない。掲載文案は次のとおり。

> 曜日や連休、営業時間、ファンスタの開催状況、イベントの節目、キャラクターの誕生日などをもとに、園内全体の混み具合を予想しています。直近の日程は天気予報も考慮し、翌日以降の予想を毎日19時ごろに更新します。スケジュールが未公開の日は、その情報を反映していない基本予想です。予想は目安であり、実際の混雑や各施設の待ち時間とは異なる場合があります。

`/daily-schedule` では日付・営業時間の下、タイムラインより上に2枚の小さな情報カードを置く。スマートフォンでも日付や閉じるボタンと横並びに詰め込まない。

```text
選択した日付　営業時間 10:00〜17:00

☀ 晴れ時々曇り              混雑予想：混雑
最高24℃／最低17℃             土曜日・クロミの誕生日
降水確率 6〜12時20％           詳しく見る →
         12〜18時20％

大分県中部／気温：大分地点
気象庁発表 前日17:00／取得 前日19:00／混雑予想更新 前日19:05
```

上記は配置・文言の例で、実際の予報ではない。気温は予報地点名と併記し、提供される項目だけを表示する。6時間単位の降水確率は元の時間区分を表示し、10〜17時の確率などに変換しない。週間予報しかない日は日単位の降水確率と対象区域を出す。現在の気温と当日最高気温を混同しない。

スケジュール上部のカード、直近7日の一覧、選択日の詳細では色と区分名を表示する。月別カレンダーの日付マスは前述の色分けのみとする。いずれの公開表示にも点数は出さない。スケジュールでキャラクターなどの絞り込みをしても、園全体の日別混雑予想は変化させない。日付変更時は対象日の保存済み結果を読み、気象庁から取得し直したり混雑度を計算し直したりしない。前の日の天気を次の日の予報として一時表示しない。

月別ページ、日別スケジュール、トップの今日の予定、必要ならMy Planに、同じ日付・同じモデル版の保存済み計算結果を渡す。各画面で別々の式を持たせない。「基本予想」「天気反映」「手動調整」を根拠として表示し、根拠のない「的中率90％」等は表示しない。予想の更新日時と天気予報の発表日時を分けて表示し、閲覧時刻を更新時刻にしない。

### キャラクターの誕生日タブ

キャラ名・誕生日・影響区分・適用される加点・判断メモを表形式で並べる。キャラ名検索と「未評価のみ」の絞り込みを用意する。

```text
キャラクター  誕生日        影響区分    適用加点    判断メモ
クロミ        登録済み月日  大きい      ＋10点      誕生日はかなり混む
通常どおりと
確認したキャラ 登録済み月日 通常どおり     0点       通常日の混雑と変わらない
未評価のキャラ 登録済み月日 未評価        暫定0点    未設定
```

月日は既存のキャラクター台帳を参照する。この画面で誕生日そのものを変える場合は台帳への導線を出し、混雑設定と二重管理しない。

各キャラは「通常どおり・小さい・大きい」の3段階から選び、対応する0・5・10点を使う。未評価は別状態として暫定0点を使う。任意の個別加点で3段階の設定を迂回する機能は設けない。基本設定の既定点を将来変更する場合は、対象キャラと予想への影響を保存前に確認できるようにする。影響区分と点数は管理用で、公開用の人気ランクとして表示しない。

### イベント・特別日タブ

- イベント名・開始日・終了日を登録し、初日・最終日・最初と最後の土日を自動表示する。加点は共通設定を継承し、必要なイベントだけ個別指定できる。
- 学校休暇は名称・対象地域・開始日・終了日を登録する。対象地域の違う休暇が重なる場合に同じ日を重複加点しない。
- 確認できた割引施策・団体来園などは対象日と理由を登録する。点数を入力する前に、既存イベント・誕生日と同じ理由を重複して数えていないか、日別の内訳で確認できるようにする。
- 非公開の管理メモと、公開ページに表示する短い理由を別欄にする。管理メモをそのまま一般利用者に出さない。

### 予想カレンダーと日付別の調整

管理画面で日付を選ぶと、適用中の混雑度、編集中の設定による混雑度、スコアの内訳、天気の発表日時、情報不足を表示する。例えば「土曜60点＋クロミの誕生日10点＝70点・混雑」を追えるようにする。天気補正は誕生日を含む合計点に同じ係数を掛けた結果として示す。公開カレンダーの色分けのみという仕様は管理画面の計算確認には適用しない。

日付ごとの調整方法は次の3つから選ぶ。

1. **自動計算**：共通ルールを使う。
2. **加点・減点**：その日だけ特別日補正を設定する。保存時と、その後の定時更新時に保存済みの天気・予定で再計算する。
3. **最終区分を指定**：その日を「混雑」などに固定する。天気更新では変えず、手動指定であることを表示する。

加点・減点と最終区分指定には理由を必須とし、最終区分指定に架空の点数を付けない。「自動計算に戻す」でその日の手動補正を解除できるようにする。確認済みの休園日は常に優先し、混雑区分で上書きしない。

### 保存前の比較・適用・復元

```text
混雑予想
[予想カレンダー] [基本設定] [キャラクターの誕生日] [イベント・特別日] [変更履歴]

設定フォーム                     選択月のプレビュー
クロミの影響  [大きい ▼] ＋10点    変更前 → 変更後
                                 区分が変わる日：○日
選択日の計算内訳                  手動で固定している日：○日

[変更を破棄]                     [保存して予想へ反映]
```

上記は構成例で、動作する画面ではない。プレビューは編集中の値で計算するが、公開ページは最後に適用した設定を使う。比較は同じ営業・予定・天気データで行い、設定の変更と天気更新の影響を混同しない。「比較対象月・データ取得時点」を表示し、未取得の月まで全件比較できたと見せない。

保存に成功した時点で設定の版を更新し、更新対象の公開ページと日別スケジュールの予想を同じ版で再計算・反映する。保持対象の過去日は元の予想・版を維持し、復元を含む設定変更で上書きしない。保存失敗時は適用中の設定を維持し、編集中の入力は残して再試行できるようにする。別の管理者が先に変更した場合は、古い設定で上書きせず差分を表示する。

変更履歴から戻す場合も、復元候補をプレビューして「保存して予想へ反映」で適用する。係数の変更によって、保存済みInstagram画像や手動の最終区分を自動で置き換えない。

未保存の編集があることを表示し、管理画面内のタブ切替では編集状態を保持する。スマートフォンではフォームの下にプレビューを置き、数値欄の横幅と操作領域を確保する。

## 実装時の構成案とデータ境界

- 天気取得・正規化：気象庁の公開XMLを毎日19時に1日1回、サーバーの定期処理で取得し、必要な情報を正規化して保存する。初期案では有料APIや登録を必要としない。公開ページの読み取り経路から取得処理を呼ばない。
- 混雑計算：入力値から同じ結果を返す共通関数。係数、適用要因、モデル版を明示する。
- 公開データ：公開・確認済み営業情報、公開・確認済み予定、公開対象として確定したイベント・補正のみ。
- 日別結果：日付、基本スコア、誕生日補正、自動スコア、自動区分、最終区分、天気未反映時の区分、手動理由、適用要因、公演スケジュール・ファンスタそれぞれの公開状況、情報の不足、天気の文言・アイコン分類・発表日時・取得日時・有効期間、対象地域・気温地点、計算日時、モデル版、定時処理の実行日・結果セットの版を分けて保持する。公開側は保存済みの結果を読むだけにする。当月内の過去日は元の値を保持し、過去月の混雑予想データは表示・保存しない。
- キャラクター別設定：キャラクターID、誕生日の混雑影響区分・加点、判断メモ、更新日時。未評価と評価済み0点を区別する。
- 管理：専用の混雑予想画面で係数、キャラ別の誕生日加点、イベント、日付単位の補正を編集する。保存前のプレビューと適用中の設定を区別し、設定の版と変更履歴を保持する。未保存編集や非公開の自由記載は公開APIに含めない。

公開APIには日付、最終混雑区分、公開用の理由、更新時刻、スケジュールとファンスタそれぞれの公開状況、情報不足、天気アイコンと元の天気文言・発表日時、判定済みのファンスタ3部屋表示フラグなど表示に必要な項目だけを返す。内部スコア、上限適用前の値、加点内訳、計算式、係数、数値境界、キャラ別の加点設定、3部屋表示用の比較基準は管理専用とし、公開API・HTML・ブラウザへ渡すページデータに含めない。公開用の理由は「連休」「営業時間が長い日」「クロミの誕生日」などの短い説明とし、管理用の計算内訳から数値付きの文をそのまま転記しない。

既存の `site-settings/instagram/crowd-calendar` は非公開の下書きであるため、ブラウザから直接公開しない。公開用のデータ契約を先に決め、サーバー側で公開してよい項目だけを返す。Storage bucketを公開に切り替える方式は使わない。

## 仕様レビュー後の整理

## 検証と導入順

1. キャラ別の誕生日加点を設定し、曜日・営業体制・イベントの仮入力で管理用の試算を確認する。平日は土日祝前後30点・その他25点、土日祝自身は別基準とし、前後の両方に当たっても重複しないことを確認する。誕生日を含む合計点に同じ天気係数が掛かることを確認する。
2. 毎日19時に1日1回の気象庁XML取得と翌日以降の予想保存を組み込み、当日・当月内の過去日を上書きしないことを確認する。日本時間の実行日、二重実行防止、失敗時の前回結果維持、月初の過去月データ削除・公開制限も確認する。過去月の予想や実績分析用の記録は蓄積しない。
3. 加点・係数・誕生日を編集し、変更前後を比較できる管理画面を実装する。無効値・保存失敗・設定復元・同時編集・休園優先・手動区分の維持・当月内の過去日固定を確認する。実際の混雑を記録するフォームは実装しない。
4. 月別ページと日別情報カードで、色分け、天気アイコン、凡例、スケジュール・ファンスタそれぞれの未公開表示、概要説明を確認する。PCの日別詳細・スマートフォンのモーダル・スケジュール上部で、最高最低気温と降水確率が表示され、降水確率は6時間単位と日単位を区別し、提供のない値を補完していないことを確認する。予報対象外・取得失敗を区別し、公開画面・API・ページデータに点数や具体的な算出方法が含まれないことを確認する。ページ表示・再読み込み・日付切替・キャッシュ切れで気象庁へのリクエストも予想の再計算も発生しないことを確認する。
